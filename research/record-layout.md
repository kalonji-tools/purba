# How can a person find a record by its kind?

The 95 records on `main` at `c6296bd` do sort by kind, but into five kinds, not four.
The fifth kind is the repository's own tooling: gates, workflows, scripts, the toolchain and the manifests.
It holds 24 records, and none of the person's four kinds takes them without a stretch.
Twelve records belong to two kinds.
Of the three forms, only a folder for each kind moves files.
A move breaks every link that crosses a folder, and a gate refuses each one.
It also breaks seven mechanisms that read the flat folder, and none of them refuses anything.
An index page moves nothing, but `main` already decides that there is no index.
A kind line moves nothing and touches all 95 records, and a gate can check its vocabulary.
The word "kind" is already a glossary term, for the kind of an error.
Three of the four sets of more than 500 records keep the kind in the record or on its pull request or issue.
Each index I could check is generated by a tool, and none is written by hand.
Kubernetes, Swift and log4brains use a folder for a kind, and MADR recommends one.

### What the four kinds miss

- **Repository tooling is a fifth kind.** Records such as `the-nightly-is-named-by-a-date` and `dependabot-proposes-each-newer-action` decide nothing about a pull request, a record or the product.
- **"How a record is written" is wider than records.** Seven of its 14 records bind only records. The other seven bind every location purba writes into, such as `a-register-belongs-to-one-location` and `a-term-belongs-to-the-glossary`.
- **"Product design" holds two halves.** Seven records say what purba is. Five say how its design proceeds, such as `a-design-in-depth-waits-for-what-it-assumes`.
- **purba's own tests cut across three kinds.** Six records decide how purba tests itself, and they sit in workflow, section and tooling.
- **A filename can mislead.** `configuration-takes-the-first-location-its-tool-reads` is about the repository's config files, and not about the product concern configuration.

### An index page by kind

**What a person sees on GitHub.** The folder page still lists 96 files. A file named `README.md` renders below that list. The `keps/` folder of Kubernetes shows this.

**What moves.** Nothing moves, and no link breaks.

**What breaks.** `lint:records` reads `docs/decisions/README.md` as a record and refuses it.
The probe shows a refusal for four missing sections and a missing Downside.
So `scripts/records.sh` and `scripts/check-records.sh` must leave it out, and `scripts/test/records.bats` changes with them.
An index outside `docs/decisions/`, such as `docs/README.md`, escapes the code owner.
`.github/CODEOWNERS` names only `/docs/decisions/`.
`a-record-names-every-location-where-it-applies` rejected `.config/records` for that reason: "It is an index, and a change to it escapes the code owner."

**What keeps it true.** A hand-written index drifts each time a record is added, renamed or deleted.

| records on `main`, by the month they were added | added |
|---|---:|
| 2026-09 | 23 |
| 2026-10 | 68 |
| 2026-11, to `c6296bd` | 8 |

The history of `docs/decisions/` also holds 4 renames and 3 deletions.
`main` has two models for a list that stays true.
`lint:gates` refuses a tracked path that `.config/gates` leaves unmarked.
`fmt:order` rewrites the order section of `LANDSCAPE.md` from its inputs.
A generated index needs the kind written down somewhere a script can read, so it needs the kind line below.

**Which records on `main` it rewrites.**

- `a-record-is-rewritten-not-amended`: "Filenames carry no numbers and there is no index." and "`ls`, `grep` and `mise run list:records` are the whole interface."
- `a-new-question-gets-a-new-record`: its Context restates that interface.

### A kind line in each record

**What a person sees on GitHub.** The folder page still lists 96 files.
The kind shows inside a record, in a code search, or in a generated list.
GitHub code search takes a `path:` qualifier and an exact phrase in quotes.

**What moves.** Nothing moves, and no link breaks.
All 95 records gain one line, and `.template.md` gains it too.
Each of those is a change to a record, so `significance-is-declared-not-detected` sends it to the code owner.

**Where the line can sit.** The probe tried a line after the reach.

| where the line sits | `lint:records` |
|---|---|
| its own paragraph after the **Reach:** paragraph | exit 0 |
| inside the **Reach:** paragraph | refused: a reach holds nothing else |

**The word.** `CONTEXT.md` L107 defines **Kind** as whether an error is a project, internal or invocation error.
`a-term-belongs-to-the-glossary` gives a term one entry.
So a `**Kind:**` line needs another word, or the glossary entry changes.

**What keeps it true.** A gate can refuse a missing line and a word outside a closed list.
Python's `check-peps.py` refuses an unknown Topic.
Kubernetes refuses an unknown `owning-sig`.
Whether the kind fits is a judgement.
`a-standard-a-gate-cannot-decide-does-not-become-a-gate` leaves that judgement to the reader.
A line can name two kinds, so the 12 records of two kinds lose nothing.

**Which records on `main` it rewrites.**

- All 95, by one line each.
- `.template.md`, for the line and its rule.
- A record that decides the line. `a-new-question-gets-a-new-record` sends a new question to a new record.
- With a generated list, the two records that the index page rewrites.

Each `kep.yaml` names `owning-sig` and `participating-sigs`. `api/proposal.go` refuses an unknown SIG against `sigs.yaml`. In the code I read, I found no check that the folder matches `owning-sig`.

  - https://github.com/rust-lang/rfcs/blob/main/README.md
  - https://github.com/rust-lang/rfcs/blob/main/generate-book.py
- **Swift Evolution.** The SE proposals sit flat in `proposals/`. One kind, the testing library, has its own folder and its own numbers, ST-0001 on.
  - https://github.com/swiftlang/swift-evolution/tree/main/proposals
  - https://github.com/swiftlang/swift-evolution/tree/main/proposals/testing

- **MADR.** Its docs say "MADR logs may be categorized ADRs by defining subdirectories". Its ADR-0010 weighs labels, a `Category:` line, YAML front matter, the filename and subfolders, and picks subfolders. Its own cons for subfolders include "when category is unknown it is hard to find the right folder". Its own log stays flat.
  - https://github.com/adr/madr/blob/develop/docs/index.md
  - https://github.com/adr/madr/blob/develop/docs/decisions/0010-support-categories.md
- **adr-tools.** `adr list` matches `^$adr_dir/[0-9]+-[^/]*\.md`, so it skips a subfolder. Its last commit is dated 2020-03-30.
  - https://github.com/npryce/adr-tools/blob/master/src/adr-list
  - https://github.com/npryce/adr-tools/blob/master/src/_adr_generate_toc
- **log4brains.** It keeps "global ADRs" in `docs/adr` and "package-specific ADRs" in `packages/<package name>/docs/adr`.
  - https://github.com/thomvaill/log4brains/blob/develop/README.md

**What the survey shows.** Four sets hold more than 500 records each.
Kubernetes, Python and Rust keep the kind in the record or on its pull request.
Swift keeps no kind line, and gives one kind a folder of its own.
Kubernetes keeps the kind in a folder and in a line at once.
Each index I could check is generated: PEP 0, the Rust book, `adr generate toc` and the log4brains site.
I did not check how the Swift dashboard builds its list.
Each set that checks a kind checks the word against a closed list, and never the fit.
